# 图库维护定时任务（z-graph GC + 快照备份链）

> 任务：TASK-20261012-027 · 范围：z-schedule 侧的定时触发
> 配套：z-graph `_doc/002_ops/01_GC可达性与回收规则.md`、z-oss `_doc/002_ops/01_备份链与滚动保留.md`

## 0. 一句话

z-schedule 按 cron 打一个任务，把三件事串成一轮：
**GC 回收（z-graph）→ 快照导出（z-graph）→ 归档 z-oss（滚动保留 N 份）**。
任一步失败 ⇒ **任务失败**（记进 job log，不会"成功但什么都没做"）。

## 1. 代码位置

| 件 | 位置 |
|---|---|
| 任务处理器 | `z-schedule-core/src/main/java/com/zifang/z/schedule/core/handler/GraphMaintenanceHandler.java` |
| Bean 装配 | `z-schedule-spring-boot-starter/.../web/config/ZScheduleAutoConfiguration.java` → `GraphMaintenanceHandlerConfiguration` |
| 行为测试 | `z-schedule-core/src/test/java/com/zifang/z/schedule/core/handler/GraphMaintenanceHandlerTest.java`（6 用例，桩 HTTP 服务） |

**bean 名 = 任务表里的执行器名**：`graphMaintenanceHandler`。
派发是按 bean 名找 handler 的（`JobTriggerServiceImpl.executeHandler` → `applicationContext.getBean(handler)`），
所以任务表里 `executor_handler` 必须填这个名字。

## 2. 任务表怎么填

| 字段 | 值 | 说明 |
|---|---|---|
| `executor_handler` | `graphMaintenanceHandler` | Bean 名（不是类名） |
| `job_cron` | `0 30 3 * * ?` | 建议凌晨 3:30（避开业务高峰） |
| `executor_param` | 见下 | 逗号/分号分隔的 `key=value` |
| `executor_route_strategy` | `FIRST` | 单机单跑即可 |
| `executor_timeout` | `0` | HTTP 超时由参数 `timeoutMs` 控制 |
| `executor_fail_retry_count` | `1` | 失败重试 1 次 |
| `trigger_status` | `1` | 启用 |

### 2.1 `executor_param` 键

| 键 | 默认 | 说明 |
|---|---|---|
| `graphUrl` | 无 | z-graph 控制面基址（如 `http://z-graph:8090`） |
| `actions` | `gc` | 逗号分隔：`gc` / `snapshot` / `archive`（`archive` 必须配 `snapshot`） |
| `keep` | 空 | GC 保留分支（逗号分隔）。**留空 = 保留全部分支**；填了就是"只有这些分支受保护" |
| `branch` | `main` | 快照分支 |
| `ossUrl` | 无 | z-oss 基址（`archive` 用） |
| `timeoutMs` | `60000` | 连接/读超时 |
| `graphToken` | 环境变量 `Z_GRAPH_API_TOKEN` | z-graph API Token |
| `ossAccessKey` | 环境变量 `ZOSS_ACCESS_KEY` | z-oss AK |
| `ossSecretKey` | 环境变量 `ZOSS_SECRET_KEY` | z-oss SK |

**凭据建议只走环境变量**：任务参数会落库，密钥进库就等于进了备份与日志。
参数可以覆盖环境变量，是为了本地调试方便，不是推荐姿势。

### 2.2 例

```
graphUrl=http://z-graph:8090;actions=gc,snapshot,archive;branch=main;ossUrl=http://z-oss:8091
```

环境变量（容器里注入，不入库）：
`Z_GRAPH_API_TOKEN=<随机长串>`、`ZOSS_ACCESS_KEY=...`、`ZOSS_SECRET_KEY=...`。

## 3. 一轮里发生什么

1. **gc**（若 actions 含 gc）：
   `POST {graphUrl}/maintenance/gc[?keep=...]`，带 `Authorization: Bearer <token>`。
   回收数从响应头 `X-Gc-Collected` 取（**不解析 JSON** —— 调度侧不该为取一个数去解 JSON）。
2. **snapshot**（若 actions 含 snapshot）：
   `POST {graphUrl}/maintenance/snapshot?branch=...`。
   - 后面**不**跟 archive 时走文件模式（z-graph 落盘，回 JSON 元数据）；
   - 后面跟 archive 时走 `&stream=true`（z-graph 直接回字节，元数据在
     `X-Commit-Id` / `X-Snapshot-Sha256` / `X-Snapshot-Bytes` 头里）。
   两种模式都用 Header 拿元数据。
3. **archive**（若 actions 含 archive）：
   把快照字节 multipart（字段名 `file`）POST 给 `{ossUrl}/api/v1/backup/archive`，
   带 `X-Zoss-Access-Key` / `X-Zoss-Secret-Key`。
   z-oss 侧归档完立刻执行滚动保留（保留最新 N 份，N 由 z-oss 的 `oss.backup.retention` 决定）。

## 4. 失败可见

- 任何一步非 2xx ⇒ 抛 `IllegalStateException`（消息里带 HTTP 状态码 + 响应体摘要）⇒
  调度侧记成**任务失败**；
- 缺参数（没配 `graphUrl`、没给 Token、`archive` 没配 `snapshot`…）⇒ **响亮失败**，
  不做"跳过这一步假装成功"；
- 每步都有 INFO 日志（回收数 / commit id / sha256 / 字节数）。

## 5. 纪律

- **生产目录首轮只观察不自动跑**：先把 `trigger_status` 置 0（停用），
  人工在测试 data-dir 上跑通一轮（见 lead 仓 `evidence/TASK-20261012-027/`）再启用。
- 演练只在**测试 data-dir** 上做，绝不对生产目录跑 GC。
- z-graph 侧的 data-dir 用规范键 `z.base.graph.data-dir`（TASK-20261012-026 定稿）。
